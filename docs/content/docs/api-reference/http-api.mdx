## Authentication

Every `/v1` and `/admin` route wants a gateway key. Send it as a Bearer token or in `x-api-key`:

```bash
curl http://localhost:8080/v1/chat/completions \
  -H "Authorization: Bearer nxs_..." \
  -H "Content-Type: application/json" \
  -d '{"model":"gpt-4o-mini","messages":[{"role":"user","content":"Hello"}]}'
```

A gateway key is `nxs_` followed by 64 lowercase hex characters. Anything else gets a 401 without touching the store. The word `Bearer` is case-insensitive, and when both headers are present `x-api-key` wins. `GET /health` is open.

Each key carries scopes. `completions` and `embeddings` let it call those routes, `models` lets it list models, and `admin` opens the `/admin` API. A key made without scopes gets `completions`, `embeddings` and `models`, and any other scope name is refused when the key is created. A route the key has no scope for answers 403. A key whose tenant is disabled, suspended or deleted answers 403 on every route, admin included, and 503 if the gateway cannot read the tenant.

Set `require_api_key: false` (or `nexus.WithRequireAPIKey(false)`) to open the `/v1` routes for local work. It opens nothing else. The admin routes always need a key with the `admin` scope, and `GET /v1/models` only asks for the `models` scope when keys are required. Even on an open gateway, any non-empty `Authorization` header counts as a key you presented, so a Basic credential or a Bearer JWT forwarded by an auth proxy gets a 401 instead of being ignored.

A WebSocket client to `/v1/realtime` authenticates with the same headers on the upgrade request. A missing or bad key gets a 401 at the handshake, before the upgrade. Once the session is running, a request the pipeline refuses (a rate limit, say) closes it with code 1008. Browsers cannot set headers on a WebSocket, so a browser client needs a proxy that adds the key.

### Your first admin key

With keys required, no HTTP route can make the first admin key, because making one takes an admin key. You do not need Go to get past that. Make a key value yourself and give it to the gateway:

```bash
export NEXUS_BOOTSTRAP_ADMIN_KEY="nxs_$(openssl rand -hex 32)"
```

A key is `nxs_` followed by 64 lowercase hex digits, and the command above makes one. When the gateway starts, after it migrates the store, it stores that value as an `admin` key named `bootstrap admin`, under a tenant with the slug `operator` (it creates the tenant if it is missing). Then use it like any key:

```bash
curl -H "x-api-key: $NEXUS_BOOTSTRAP_ADMIN_KEY" http://localhost:8080/admin/providers
```

Starting again changes nothing, because the key is found by its hash. If you revoke the bootstrap key, it stays revoked and the gateway logs a warning with its id on each start. Take the value out of your config, or set a new one to get a fresh key. If the `operator` tenant is disabled or suspended, start fails with an error that names it.

Inside Forge, set `bootstrap_admin_key` under `extensions.nexus`, or leave it empty and use the environment variable (see the [Forge extension guide](/docs/guides/forge-extension)). Without the extension, pass `nexus.WithBootstrapAdminKey(raw)` and call `gw.EnsureBootstrapAdminKey(ctx)` after `Initialize` and `Store().Migrate()`.

If you would rather make the key in Go, once, from the process that owns the gateway, this works too:

```go
t, err := gw.Tenants().Create(ctx, &tenant.CreateInput{Name: "Ops", Slug: "ops"})
if err != nil {
    return err
}
_, raw, err := gw.Keys().Create(ctx, &key.CreateInput{
    TenantID: t.ID.String(),
    Name:     "ops",
    Scopes:   []string{"admin"},
})
if err != nil {
    return err
}
// raw is shown once. Only its hash is stored, so hand it to its owner now.
```

`Create` returns the raw key this once. Only its hash is stored, so if you lose it you rotate or revoke the key and make another. The dashboard uses its own operator authentication and calls the services in process; it does not need a gateway admin key. An `admin` key administers every tenant through the HTTP API, whichever tenant it belongs to, so keep it out of application code, source control and logs.

## OpenAI-Compatible Endpoints

Two packages serve these routes, and both are plain `net/http` handlers you mount wherever you like:

| Handler | Routes |
|---------|--------|
| `proxy.New(gw.Engine())` | The `/v1` routes below, `GET /health` and `/v1/realtime` |
| `api.New(gw).Handler()` | The same, plus the `/admin` API |

Neither the gateway nor the Forge extension mounts them for you. Both take `WithStreamEncoder`, `WithWebSocket(opts)` and `WithoutWebSocket()` options, and the proxy also has `WithStreamEncoderAlias`.

### Chat Completions

```
POST /v1/chat/completions
```

The request and response follow OpenAI's chat completions format. Set `stream: true` to stream; the wire format comes from `?stream_format=` or the `Accept` header (see the [Streaming API](/docs/api-reference/streaming-api)).

### Embeddings

```
POST /v1/embeddings
```

Embeddings go to the provider the body names in `provider`, else to an embeddings provider that lists the model, else to the first registered provider that can embed. See [Routing](/docs/core/routing#embeddings).

### Models

```
GET /v1/models
GET /v1/models/{model}
```

Lists the built-in model catalog of every registered provider, in OpenAI's list shape. Aliases aren't included. The `id` field currently holds each model's display name (`GPT-4o`) rather than its model ID (`gpt-4o`), and `GET /v1/models/{model}` matches on that same display name. Both need the `models` scope when keys are required.

### Realtime

```
GET /v1/realtime   (WebSocket upgrade)
```

A bidirectional WebSocket session over the same pipeline. See the [Streaming API](/docs/api-reference/streaming-api).

## Admin Endpoints

Bad input (a missing name, a tenant id that does not parse, an unknown scope) is a 400 `invalid_request` with the reason. A tenant or key that does not exist is a 404. Any other failure is a 500 that says only `internal error`, and the cause goes to the gateway log.

### Tenants

| Method | Path | Description |
|--------|------|-------------|
| `GET` | `/admin/tenants` | List tenants, newest first; filter with `?status=` and `?search=`, page with `?cursor=` |
| `POST` | `/admin/tenants` | Create a tenant |
| `GET` | `/admin/tenants/{id}` | Get a tenant |
| `PATCH` | `/admin/tenants/{id}` | Update a tenant |
| `DELETE` | `/admin/tenants/{id}` | Delete a tenant |

Deleting a tenant that still has keys or usage history answers 409 `conflict`: disable it instead. This check applies across the built-in stores when you use the gateway's tenant service.

### API Keys

| Method | Path | Description |
|--------|------|-------------|
| `GET` | `/admin/keys?tenant_id=...` | List a tenant's keys (`tenant_id` is required) |
| `POST` | `/admin/keys` | Create a key; the response carries the raw key once |
| `DELETE` | `/admin/keys/{id}` | Revoke a key |

### Usage

| Method | Path | Description |
|--------|------|-------------|
| `GET` | `/admin/usage?tenant_id=...&period=month` | Usage summary for one tenant. `tenant_id` is required; `period` is `day`, `week` or `month` (the default) |

### Providers

| Method | Path | Description |
|--------|------|-------------|
| `GET` | `/admin/providers` | List registered providers |

### Health

| Method | Path | Description |
|--------|------|-------------|
| `GET` | `/health` | Gateway health check, open to everyone |

## Response Headers

Every `/v1` and `/admin` response carries `X-Request-Id`. It is the id on the request's usage record, so you can match a client error to a row in the usage store. The gateway makes its own id and ignores one the client sends.

Other headers show up when they apply:

| Header | When |
|--------|------|
| `Retry-After` | A 429 that says how long to wait. Whole seconds, rounded up. |
| `WWW-Authenticate: Bearer` | Every 401. |

The gateway sets no `X-Nexus-*` headers. The provider that served the request, whether the response came from the cache, and the latency are on the usage record. See [Errors](/docs/concepts/errors) for the error body and the refusal codes.
